# 邻动项目 1.0 交接说明

更新时间：2026-04-28

## 1. 项目概述

邻动项目当前已基本完成 1.0 主体开发，现阶段处于“等待备案通过后，补齐正式支付与正式退款能力”的收口阶段。

当前项目不是单一应用，而是一套围绕微信小程序业务搭建的完整交付体系，包含：

- 家长端微信小程序
- 运营后台 Web 端
- 小程序业务后端服务
- 后台管理接口服务
- 首页定位相关微信云函数
- MySQL 数据库
- CloudBase 云托管与静态托管部署链路

项目当前业务核心是“课包拼团”，面向家长提供课程浏览、开团、参团、订单支付、拼团查看等能力，面向运营提供课包配置、拼团管理、订单管理、Banner 管理、账号权限、日志追踪等能力。

## 4. 核心技术架构

## 4.1 总体架构

当前项目建议按“四端两服务一库一函数”理解：

- 小程序前端：微信原生小程序
- 后台前端：React 管理后台
- 小程序服务端：`lindong-api`
- 后台服务端：`lindong-console-api`
- 数据库：MySQL
- 云函数：`ip-geolocation`

其中：

- 小程序通过 `wx.cloud.callContainer` 调用云托管服务
- 后台前端通过 HTTP 调用后台接口
- 两套服务端共用 `backend/shared/*` 中的业务规则与部分领域服务

## 4.2 前端技术栈

### 小程序端

- 微信原生小程序
- `WXML + WXSS + JavaScript`
- `weui-miniprogram`
- `style: v2`
- `glass-easel`
- `lazyCodeLoading`

### 后台前端

- React 19
- TypeScript
- Vite 6
- React Router 7

## 4.3 后端技术栈

- Node.js
- Express
- JWT
- MySQL
- dotenv
- CloudBase 云托管

## 4.4 项目目录结构

建议交接时重点认这几个目录：

- `miniprogram/`：微信小程序主工程
- `console/`：运营后台前端

- `backend/lindong-api/`：小程序正式部署目录
- `backend/console-api-service/`：后台接口正式部署目录
- `backend/shared/`：共享业务规则与服务
- `cloudfunctions/ip-geolocation/`：定位与地址解析云函数
- `qa/regression/`：Playwright 回归测试
- `docs/`：产品、技术、部署、交接文档

## 5. 部署方案

## 5.1 当前推荐部署形态

### 小程序侧

- 前端载体：微信小程序
- 服务调用：`wx.cloud.callContainer`
- 云托管服务：`lindong-api`
- 正式部署目录：`backend/lindong-api`

### 后台侧

- 后台前端：CloudBase 静态托管
- 后台接口：CloudBase 云托管
- 后台前端源码目录：`console/`
- 后台接口部署目录：`backend/console-api-service`

### 辅助能力

- 首页定位与地址搜索：微信云函数 `cloudfunctions/ip-geolocation`

## 5.2 部署注意事项

- 小程序后端发布时，必须以 `backend/lindong-api` 为准，不能只改混合源码目录后不同步部署目录
- 后台接口发布时，必须确认 `backend/console-api-service` 已同步最新代码
- 首页定位问题优先检查云函数，不要误判为主后端问题
- 后台静态托管必须配置 SPA 路由回退到 `index.html`

## 5.3 数据库与环境

当前主数据层为 MySQL。

建议交接时同步确认以下内容：

- MySQL 库实例信息
- CloudBase 环境 ID
- 小程序 AppID
- 云托管服务名
- 后台静态托管站点
- 后台接口访问域名

- 支付相关商户配置

## 5.4 发布步骤

建议每次发布都按“先校验、再发布、再验收”的固定顺序执行，不要跳步骤。

### 5.4.1 发布前通用检查

发布前至少确认：

- 本次改动影响范围是小程序后端、后台前端、后台后端，还是云函数
- 对应正式部署目录是否已经更新
- 若涉及数据库字段、状态流转、订单逻辑，是否需要先执行 migration
- 环境变量、密钥、域名、回调地址是否齐全
- 已完成本地回归测试和代码安全审查

### 5.4.2 小程序后端发布步骤

正式部署目录：

- `backend/lindong-api`

建议步骤：

1. 确认本次变更已在 `backend/lindong-api` 中，而不是只存在于混合源码目录。
2. 若涉及数据库结构调整，先执行目标环境 migration。
3. 检查 CloudBase 云托管环境变量是否齐全，尤其是支付、登录、数据库相关配置。
4. 在 CloudBase 中以 `backend/lindong-api` 作为 GitHub 构建根目录重新部署。
5. 部署完成后先验证健康接口和核心 API。
6. 再用小程序开发版 / 体验版做真机或半真机冒烟验证。

建议发布后至少验证：

- 登录
- 首页课程列表
- 课程详情
- 创建订单
- mock 支付成功链路
- 我的拼团

若是正式支付阶段，还要追加验证：

- 统一下单
- `wx.requestPayment`
- 支付回调落库
- 支付成功后人数、订单、拼团状态一致

### 5.4.3 后台接口发布步骤

正式部署目录：

- `backend/console-api-service`

建议步骤：

1. 确认本次变更已同步到 `backend/console-api-service`。
2. 若涉及后台课包字段、订单字段或状态规则，先确认目标库 migration 已执行。
3. 检查 CloudBase 云托管环境变量，至少包括 MySQL、JWT、存储相关配置。
4. 在 CloudBase 中以 `backend/console-api-service` 为构建根目录重新部署。
5. 部署完成后先验证：
   - `GET /health`
   - `POST /api/admin/login`
   - `GET /api/admin/dashboard/overview`
6. 再验证关键管理接口，如课包列表、订单列表、账号列表。

### 5.4.4 后台前端发布步骤

源码目录：

- `console/`

建议步骤：

1. 本地执行：
   - `npm install`
   - `npm run lint`
   - `npm run build:cloudbase`
2. 确认 `VITE_API_BASE_URL` 指向当前后台接口域名。
3. 确认 CloudBase 静态托管配置：
   - Root Directory=`console`
   - Output Directory=`dist`
4. 确认 SPA 路由回退仍配置为 `index.html`。
5. 发布静态资源。
6. 发布后验证登录页、dashboard、课包列表、子路由刷新。

### 5.4.5 定位云函数发布步骤

云函数目录：

- `cloudfunctions/ip-geolocation`

建议步骤：

1. 确认改动已同步到云函数目录。
2. 检查云函数环境变量，重点是 `TENCENT_MAP_KEY`。
3. 将云函数部署到当前 CloudBase 环境。
4. 发布后验证首页定位、地址搜索、手动切换位置。

### 5.4.6 数据库 migration 发布步骤

若改动涉及表结构、状态机字段或后台新能力，必须把 migration 当成正式发布步骤的一部分。

建议顺序：

1. 备份目标表或目标库。
2. 执行 migration。
3. 校验字段、索引、默认值是否正确落库。
4. 再发布依赖该结构的后端服务。
5. 最后发布前端并做联调验证。

原则：

- 代码发布不能替代数据库变更
- 数据库新增字段后，不建议因应用层异常立即物理回滚字段
- 优先回滚应用代码，再决定是否处理数据库结构

## 5.5 发布后回归与验收要求

每次部署上线，无论是预发布、体验版、试运行，还是正式生产发布，都必须执行回归测试。

最低要求：

- 有代码改动，就必须回归
- 有数据库变更，就必须回归
- 有支付、订单、拼团、后台配置相关改动，就必须做重点回归

建议至少按下面顺序验收：

1. 服务可用性检查
2. 自动化测试
3. 核心业务冒烟
4. 如涉及资金链路，再做支付/退款专项验证

## 6. 当前关键环境与运行关系

当前运行关系建议理解为：

1. 家长在小程序内访问前台业务
2. 小程序通过 CloudBase 容器调用 `lindong-api`
3. `lindong-api` 访问 MySQL 并处理拼团、订单、登录等业务
4. 运营人员在浏览器访问后台静态站点
5. 后台前端调用 `lindong-console-api`
6. `lindong-console-api` 访问同一套 MySQL 主数据
7. 首页定位与地址搜索额外依赖 `ip-geolocation` 云函数

## 6.3 每次部署上线必须进行代码安全审查

每次部署上线前，除了功能回归，还必须完成代码安全审查。

当前仓库并没有一套完整自动化安全审计体系，因此安全审查需要以“代码 review + 配置检查 + 关键链路复核”方式执行。

至少要检查：

- 是否误提交密钥、证书、token、数据库密码
- 环境变量是否只保存在正确的平台或密钥管理位置
- 管理后台鉴权和权限控制是否被绕过
- 是否存在测试开关、mock 开关误带到生产
- 支付回调、退款、订单状态更新是否具备幂等保护
- 上传、跳转、富文本等高风险入口是否存在明显注入或滥用风险
- CORS、鉴权头、CloudBase 身份头信任逻辑是否仍符合当前部署方案
- 日志中是否输出敏感信息

建议每次发布前至少安排一次人工 review，重点关注：

- `backend/lindong-api`
- `backend/console-api-service`
- `console`
- 支付、订单、登录、权限、上传相关改动

原则上：

- 未完成回归测试，不允许发布
- 未完成安全审查，不允许发布

### 7.6 已知问题与坑点

建议把下面这些问题当成“高频排障入口”，不要只把它们当作历史备注。

#### 7.6.1 正式部署目录与混合源码目录不是同一套

当前仓库里 `backend/` 既是混合源码目录，又派生出正式部署目录：

- 小程序后端正式部署目录：`backend/lindong-api`
- Console 后端正式部署目录：`backend/console-api-service`

高风险点：

- 只改 `backend/` 中的源码，不同步到正式部署目录，线上不会生效
- 本地联调正常，不代表云托管部署包已经同步
- 支付、订单、我的拼团这类链路最容易因“部署包还是旧代码”而误判

建议交接时明确要求：

- 每次发布前，先确认正式部署目录中的关键文件是否已同步
- 若线上行为与本地不一致，优先检查部署目录而不是先怀疑数据库或前端缓存

#### 7.6.2 小程序主后端与定位云函数是两套独立部署物

首页定位、地址搜索不走 `lindong-api`，而是依赖微信云函数：

- `cloudfunctions/ip-geolocation`

高风险点：

- 首页定位异常，不一定是小程序主后端问题
- 云函数未部署、环境变量未配置、缓存表未建，都会表现为定位异常或地址搜索失败
- 容易出现“小程序接口正常，但首页位置一直回默认值”的误判

建议排障顺序：

1. 先看云函数是否已部署到正确 CloudBase 环境
2. 再看 `TENCENT_MAP_KEY` 是否已配置
3. 再看 `ip_location_cache` 集合或相关缓存资源是否存在

#### 7.6.3 前台“课程”与后台“课包”是同一业务，但命名长期不一致

当前口径是：

- 家长端前台统一使用“课程”
- 后台、数据库、接口大量沿用 `package / course_package`

高风险点：

- 新接手的人容易误以为“课程”和“课包”是两个并行业务
- 查接口、查数据库、查后台页面时会因为关键词不一致而漏看文件
- 产品文档和技术文档在不同阶段可能混用两套名称

建议理解方式：

- 当前 1.0 主业务本质上就是“课包拼团”
- 只是前台为了用户理解成本，文案层统一显示为“课程”

#### 7.6.4 历史单次课程拼团逻辑仍有残留，不应误当当前主链路

仓库保留了早期“单次课程拼团”阶段的一部分代码、表结构、文档和命名。

高风险点：

- 搜索关键词时容易读到旧逻辑
- 某些目录、字段或接口仍沿用历史命名
- 如果不先确认文档日期和当前有效口径，容易按旧方案继续改代码

建议处理方式：

- 查资料优先看“current / integrated / handoff / cutover”类文档
- 对早期 PRD、早期技术稿、早期 Supabase 方案保持警惕
- 改动前先确认当前主链路是否已经切到 MySQL + CloudBase

#### 7.6.5 接口命名与接口实际语义并不总是完全一致

典型例子：

- `GET /api/courses/:id/active-group`

这个名字看上去像“只返回进行中的团”，但历史实现里在没有进行中团时，可能回退到最近成功团或失败团。

高风险点：

- 前端看到接口名就按“当前活跃团”理解
- 倒计时、按钮文案、团状态判断容易误判
- 后续开发容易在“接口名”和“真实返回语义”之间踩坑

建议处理方式：

- 不要只相信接口名，要以当前实现和当前文档为准
- 涉及团状态判断时，优先查看后端返回字段的完整语义

#### 7.6.6 mock 降级曾掩盖过真实问题，核心链路不能默认相信页面展示

历史联调阶段，小程序部分页面存在“真实请求失败后 fallback 到 mock”的策略。

高风险点：

- 页面看起来有数据，但不一定来自真实后端
- 首页人数、课程详情、支付相关状态容易被假数据误导
- 会出现“数据库查不到，前端却展示正常”的排障假象

当前建议：

- 首页、课程详情、订单、支付、拼团详情等核心链路优先以真实接口报错为准
- 如发现展示与数据库不一致，优先排查是否走了 mock 或本地兜底

#### 7.6.7 支付成功才算入团，这是一条跨页面、跨接口的系统规则

当前有效规则是：

- 创建订单未支付前，不增加人数
- 支付成功后，才写入成员并更新拼团人数
- “我的拼团”也应以支付成功为准

高风险点：

- 如果只修订单接口，不同步检查课程详情、拼团详情、我的拼团，就会出现状态错位
- 正式支付接入时，如果幂等、回调、前端成功态确认没统一好，最容易造成重复入团或假成功

这条规则后续在接正式微信支付时必须再次全链路复核。

#### 7.6.8 正式支付与正式退款尚未真正收口完成

截至 2026-04-28：

- 仓库内已有正式支付接入配置入口
- 小程序和服务端文档已定义真实微信支付口径
- 但 1.0 的最终收口仍依赖备案、商户参数、回调配置、真实联调

高风险点：

- 容易误以为“有支付代码 = 已完成支付上线”
- 实际上正式商户号、证书、回调域名、回调验签、退款证书等外部条件仍可能未完全到位

建议把“正式支付是否真的可用”当成独立交接项，不要只看代码状态。

正式微信支付云调用接入和部署检查见 `docs/deploy/2026-05-07-wechat-cloudpay-runbook.md`。

#### 7.6.9 后台静态托管存在 SPA 路由刷新 404 风险

后台前端使用 React Router。

高风险点：

- 若 CloudBase 静态托管未配置 `index.html` 回退
- `/packages`、`/package-orders` 等子路由刷新会直接 404

这类问题经常被误判为前端构建失败，实际上是静态托管配置问题。

#### 7.6.10 课包新字段和状态规则依赖数据库 migration，代码发布不能替代数据库变更

后台课包管理已经扩展过新的字段和状态规则，例如：

- `class_count`
- `class_duration_minutes`
- `group_price_config`
- `publish_time`
- `unpublish_time`

高风险点：

- 只发前后端代码，不执行 MySQL migration，会导致页面打开报错或数据回显异常
- 旧数据即使结构兼容，也不代表已经具备新业务字段

建议任何涉及后台课包字段问题的排障，先确认目标库是否执行过对应 migration。

#### 7.6.11 文档口径更新并非完全同步，必须优先认“当前有效版”

仓库文档较多，且经历过：

- 单次课程拼团阶段
- Supabase 方案阶段
- MySQL 迁移阶段
- Cloudflare / CloudBase 多轮切换阶段

高风险点：

- 同一主题可能存在多版文档
- 旧文档仍保留在仓库中，容易被当成当前方案

建议：

- 优先看文档名里含 `current`、`integrated`、`handoff`、`cutover`、明确日期且较新的文件
- 交接时明确告知“旧文档可参考背景，但不能直接作为现行方案”

这部分越明确，交接质量越高。
