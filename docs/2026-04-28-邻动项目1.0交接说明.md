# 邻动项目 1.0 交接说明

更新时间：2026-05-11

## 1. 项目概述

邻动当前不是单一应用，而是一套围绕微信小程序业务搭建的完整交付体系，当前主业务已经收口到“5 节课课包拼团”。

当前正式交付范围包含：

- 家长端微信小程序
- 运营后台 Web 端
- 小程序业务后端 `lindong-api`
- 后台管理接口 `console-api-service`
- MySQL 主数据层
- CloudBase 云托管 / 静态托管部署链路
- 首页定位云函数与定时任务云函数
- 回归测试与上线校验脚本

项目当前最重要的业务链路是：

- 课程/课包浏览
- 开团 / 参团
- 下单与微信原生支付
- 拼团成功 / 失败后的状态推进
- 后台课包、拼团、订单、账号、日志管理

### 3.1 家长端微信小程序

当前已覆盖的主要功能：

- 启动协议确认

- 首页课程/课包列表展示

- 课程/课包详情展示

- 参团支付确认页
- 微信原生支付
- 支付结果页
- 拼团详情页
- 我的拼团列表
- 我的页面
- 分享拼团
- 拼团结果订阅通知
- 小程序最近使用 / 列表重开首页收口
- 终态团旧分享链接回课程详情 / 首页

当前业务规则重点：

- 当前主业务已从早期“单次课程拼团”收口为“5 节课课包拼团”
- 前台文案多使用“课程”，后台与接口仍大量沿用 `package`
- 创建订单未支付前，不计入拼团人数
- 支付成功后，才真正写入拼团成员并更新人数
- 参团支付在团名额临界时，后端必须保证最后一个名额只能成功一笔，未抢到名额的支付成功单需直接进入退款链路
- 退款中间态期间，不提前扣减首页/详情页中的团人数与展示，只有订单最终进入 `refunded` 才真正释放名额
- 若订单或支付记录已进入 `refund_pending / refund_failed / refunded`，后续重复支付成功回调不得再把它写回普通成功态
- 成团当天如果刚好就是用户选择的上课星期，首课时间必须顺延到下一周同一星期和整点，不能“当天成团当天上课”
- 拼团详情页在进行中状态下，需要在上课地点下方展示 `拼团剩余时间`
- 拼团详情页是“单团视角”，不承接课程维度聚合展示
- 从微信“小程序最近使用 / 列表”重新打开时，默认回首页；但分享卡片、订阅通知、支付回跳等明确目标页入口仍保留原落地页
- 用户通过分享链接访问已失败、已取消、已隐藏的团，或当前查看者因退款态被限制查看详情时，前端统一提示“当前拼团已结束，您可另外开团”，并跳该团对应课程详情页；课程不可访问时回首页

## 4. 核心技术架构

### 4.1 总体架构

当前项目建议按“前台一端、后台一端、两套服务、一套 MySQL、若干辅助云函数/任务”来理解：

- 小程序前端：`miniprogram/`
- 后台前端：`console/`
- 小程序业务后端：`backend/lindong-api/`
- 后台接口后端：`backend/console-api-service/`
- 数据库：MySQL
- 云函数：`ip-geolocation`、`lindong-cron`

其中：

- 小程序通过 `wx.cloud.callContainer` 调用 `lindong-api`
- 后台前端通过 HTTP 调用 `console-api-service`
- 两套服务端共用 `backend/shared` 风格的业务规则与部分领域逻辑
- `wechat-pay`、`wechat-pay-callback` 相关代码仍保留在仓库中，但不再是当前主支付链路

### 4.2 前端技术栈

#### 小程序端

- 微信原生小程序
- `WXML + WXSS + JavaScript`
- `weui-miniprogram`
- `style: v2`
- `glass-easel`
- `lazyCodeLoading`

#### 后台前端

- React 19
- TypeScript
- Vite 6
- React Router 7

### 4.3 后端技术栈

- Node.js
- Express
- JWT
- MySQL
- dotenv
- CloudBase 云托管
- 仓库内保留 Wrangler / Worker 入口，用于部分运行与调试能力

### 4.4 当前关键目录

建议交接时重点认这几个目录：

- `miniprogram/`：微信小程序主工程
- `console/`：运营后台前端
- `backend/`：后端源码与脚本总目录
- `backend/lindong-api/`：小程序正式后端部署目录
- `backend/console-api-service/`：后台接口正式部署目录
- `backend/migrations/`：MySQL migration
- `cloudfunctions/ip-geolocation/`：定位与地址解析云函数
- `cloudfunctions/lindong-cron/`：定时触发内部任务云函数
- `qa/regression/`：Playwright 与小程序逻辑回归
- `docs/`：产品、技术、部署、交接文档

注意：

- `frontend/` 是早期独立前端原型，不是当前主业务入口
- `docs/console/邻动体适能运营后台/` 是文档型原型工程，不是当前正式后台入口

## 5. 支付、退款与通知链路

### 5.1 当前支付主链路

当前支付链路是“微信原生支付”，不是“支付云函数主导的云调用支付”。

当前主链路为：

1. 小程序创建订单
2. 小程序调用后端 `/api/payments/prepare`
3. 后端按当前 `PAYMENT_PROVIDER_MODE=wechat` 生成统一下单参数
4. 小程序直接调用 `wx.requestPayment()`
5. 微信支付成功后，微信回调 `lindong-api` 的支付回调接口
6. 后端按 `orders` 与 `payment_records` 做幂等落库
7. 后端执行入团、人数更新、成团、退款竞争收口等业务逻辑

### 5.2 当前退款链路

当前退款能力已包含：

- 后台手动退款
- 满员竞争失败后的退款收口
- 退款中间态与终态同步
- 退款失败收口

当前需要特别关注：

- `refund_pending` 期间不要提前释放人数
- 支付回调与退款回调可能并发或先后交错到达
- 重复支付成功回调不能覆盖退款态

### 5.3 订阅通知链路

当前已接入拼团结果订阅通知，相关链路包括：

- 小程序支付结果页 / 拼团详情页发起订阅
- 后端记录订阅状态与通知任务
- `cloudfunctions/lindong-cron` 定时触发内部处理接口
- 后端调用微信订阅消息接口执行投递

### 5.4 仓库内保留但非当前主链路的支付代码

仓库中仍保留：

- `cloudfunctions/wechat-pay/`
- `cloudfunctions/wechat-pay-callback/`
- `backend/lindong-api/routes/payments.js` 中的部分 `cloudpay` 内部路由

这些内容当前更适合视为“历史接入 / 备用能力 / 调试资产”，不要把它们误认为当前正式支付主链路。

## 6. 部署方案

### 6.1 当前推荐部署形态

#### 小程序侧

- 前端载体：微信小程序
- 服务调用：`wx.cloud.callContainer`
- 云托管服务：`lindong-api`
- 正式部署目录：`backend/lindong-api`

#### 后台侧

- 后台前端：CloudBase 静态托管
- 后台接口：CloudBase 云托管
- 后台前端源码目录：`console/`
- 后台接口部署目录：`backend/console-api-service`

#### 辅助能力

- 首页定位与地址搜索：`cloudfunctions/ip-geolocation`
- 定时内部任务：`cloudfunctions/lindong-cron`

### 6.2 部署注意事项

- 小程序后端发布时，必须以 `backend/lindong-api` 为准，不能只改混合源码目录后不同步部署目录
- 后台接口发布时，必须确认 `backend/console-api-service` 已同步最新代码
- 首页定位问题优先检查 `ip-geolocation`
- 订阅通知问题优先检查 `lindong-cron` 与后端内部处理接口
- 后台静态托管必须配置 SPA 路由回退到 `index.html`

### 6.3 建议同步确认的环境信息

- MySQL 实例与账号信息
- CloudBase 环境 ID
- 小程序 AppID
- 云托管服务名
- 后台静态托管站点
- 后台接口访问域名
- 支付相关商户配置
- 订阅通知模板 ID
- 云函数环境变量

## 8. 当前关键运行关系

当前运行关系建议理解为：

1. 家长在小程序内访问前台业务
2. 小程序通过 CloudBase 容器调用 `lindong-api`
3. `lindong-api` 访问 MySQL 并处理拼团、订单、登录、支付、通知等业务
4. 支付时，小程序直接走微信原生 `wx.requestPayment`
5. 微信支付结果回调 `lindong-api`
6. 运营人员在浏览器访问后台静态站点
7. 后台前端调用 `console-api-service`
8. `console-api-service` 访问同一套 MySQL 主数据
9. 首页定位与地址搜索依赖 `ip-geolocation`
10. 拼团结果通知定时任务依赖 `lindong-cron`

## 9. 当前高风险点

交接时最容易踩坑的点如下：

- 文案层常说“课程”，但代码与接口大量沿用 `package`
- 仓库里存在历史/备用支付实现，当前正式口径必须认“微信原生支付”
- 小程序主入口是 `miniprogram/`，不是 `frontend/`
- 后台主入口是 `console/`，不是 `docs/console/邻动体适能运营后台/`
- 订单创建成功不等于参团成功，只有支付成功才真正入团
- 退款中间态与支付成功回调存在并发竞争，不能只看单表状态
- 最后一个名额的并发支付是核心高风险场景
- 分享链接落地、最近使用重开首页、订阅通知落地页这几类入口容易回归破坏

## 10. 建议优先交接清单

建议正式交接时，优先把下面内容一次性讲清楚：

1. 哪些目录是当前正式入口，哪些只是原型/历史资产
2. 当前支付主链路是“微信原生支付”，不是“支付云函数主链路”
3. 后端正式部署目录与后台接口正式部署目录分别是什么
4. MySQL、CloudBase、支付商户、后台账号、订阅模板等环境资产由谁持有
5. 上线前必须执行哪些验证命令和回归动作
6. 哪些业务规则属于绝不能改坏的红线：人数、退款、最后名额、首课日期、分享兜底、入口收口

以上内容如果交接清楚，接手人就能较快分辨“当前真实链路”“仓库历史资产”和“上线前必须守住的业务红线”。
