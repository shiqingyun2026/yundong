# 编号规则改造任务清单

## 1. 目标

- 让 `console` 内展示的课包编号、拼团编号、订单号更有规律、便于运营识别和沟通。
- 课包主键改为规则字符串。
- 拼团主键改为规则字符串。
- 订单主键保留 UUID。
- 订单号改为规则字符串。

建议采用以下编号方案：

- 课包 ID：`PKG-YYYYMMDD-####`
- 拼团 ID：`PG-YYYYMMDD-#####`
- 订单号：`LDPKG-YYYYMMDD-######`

说明：

- `course_packages.id` 直接改为规则主键。
- `package_groups.id` 直接改为规则主键。
- `orders.id` 保留 UUID，继续承担内部主键职责。
- `orders.order_no` 作为运营和业务可读编号，改为规则化生成。

## 2. 范围

本次改造涉及：

- 数据库表结构与索引。
- 编号生成规则与并发流水控制。
- 课包创建逻辑。
- 拼团创建逻辑。
- 订单创建逻辑。
- console 页面展示文案与筛选口径。
- 后端单测、前端回归、测试种子数据。

本次不包含：

- 已上线历史生产数据迁移。
- 小程序端展示文案重构以外的业务流程调整。
- 支付渠道协议字段改造。

## 3. 核心原则

- 主键和业务编号职责分离：
  - 课包、拼团直接使用规则主键。
  - 订单保留 UUID 主键，仅调整 `order_no`。
- 流水号必须通过服务端统一生成，不允许前端拼接。
- 流水号生成必须支持并发，不能使用“查最大值 + 1”。
- 旧测试数据和种子数据需全部同步为新规则，避免混用。

## 4. 数据库任务

### 4.1 新增流水号表

- 新增业务流水表，例如：`biz_serial_counters`。
- 字段建议：
  - `biz_type`
  - `biz_date`
  - `current_seq`
  - `created_at`
  - `updated_at`
- 唯一索引建议：
  - `uniq_biz_type_date (biz_type, biz_date)`

### 4.2 调整主表字段

- 确认 `course_packages.id` 字段长度可容纳规则 ID。
- 确认 `package_groups.id` 字段长度可容纳规则 ID。
- 确认 `orders.order_no` 字段长度可容纳新单号。
- 复查并调整以下关联字段长度：
  - `orders.package_id`
  - `orders.package_group_id`
  - `payment_records.package_id`
  - `payment_records.package_group_id`
  - 其他引用 `course_packages.id`、`package_groups.id` 的外键字段

### 4.3 调整索引与外键

- 更新所有引用 `course_packages.id` 的外键定义。
- 更新所有引用 `package_groups.id` 的外键定义。
- 复查相关索引长度，避免规则字符串后索引失效或性能下降。

## 5. 后端实现任务

### 5.1 新增编号生成器

- 在仓库层或共享工具层新增统一编号生成模块。
- 提供至少以下方法：
  - `buildPackageId(now)`
  - `buildPackageGroupId(now)`
  - `buildPackageOrderNo(now)`
- 输出格式：
  - `PKG-20260428-0001`
  - `PG-20260428-00001`
  - `LDPKG-20260428-000001`

### 5.2 实现并发安全流水分配

- 在一个事务内按 `biz_type + biz_date` 原子递增。
- 推荐使用：
  - `insert ... on duplicate key update`
  - 或显式事务 + 行锁
- 需要区分三类流水：
  - `PKG`
  - `PG`
  - `LDPKG`

### 5.3 改造课包创建

- 修改 `coursePackagesRepository.createPackage`。
- 新建课包时不再走 UUID，改为规则 `PKG-*`。
- 保证复制课包、新建课包、后台创建接口全部走统一生成逻辑。

### 5.4 改造拼团创建

- 修改 `packageGroupsRepository.createPackageGroup`。
- 新建拼团时不再走 UUID，改为规则 `PG-*`。
- 保证开团成功创建拼团、自动成团相关链路都使用统一规则。

### 5.5 改造订单单号生成

- 修改 `ordersRepository.createOrder` 与 `_helpers.buildOrderNo`。
- `orders.id` 继续使用 UUID。
- `order_no` 改为新的 `LDPKG-*` 规则。
- 如单次课程订单仍在系统中保留，需评估是否同步统一其单号前缀策略。

### 5.6 全链路排查引用点

- 排查所有通过 `package_id` 查询课包的服务。
- 排查所有通过 `package_group_id` 查询拼团的服务。
- 排查支付、退款、支付记录、通知、日志、列表搜索、详情跳转中的 ID 使用点。
- 确保没有代码隐式假设这些字段是 UUID 或固定 36 位长度。

## 6. Console 前端任务

### 6.1 页面展示口径

- 课包管理列表继续展示课包编号，但需确认文案是否从“ID”调整为“课包编号”。
- 课包拼团列表、详情页统一展示“拼团编号”。
- 课包订单列表、详情页统一展示“订单号”，避免将内部 `orders.id` 暴露为主查询信息。

### 6.2 搜索与跳转

- 课包列表搜索如支持按编号搜索，需兼容 `PKG-*`。
- 拼团列表搜索如支持按拼团 ID 搜索，需兼容 `PG-*`。
- 订单搜索优先按 `order_no` 查询，兼容新规则 `LDPKG-*`。
- 所有 console 页面之间的跳转链接继续以真实主键字段为准。

### 6.3 文案与字段命名

- 将前端“ID”文案尽量改成“编号”或“订单号”。
- 避免把内部主键和业务单号混用，减少运营理解成本。

## 8. 风险点

- 规则 ID 长度变化导致外键字段长度不足。
- 某些代码可能默认把 ID 当 UUID 处理。
- 某些日志、支付、通知逻辑可能把 `id` 或 `order_no` 直接拼接到上下文中。
- 并发创建时若流水生成不原子，可能出现重复编号。
- 订单号若进入支付侧，需要确认长度、字符集和唯一性约束。

## 9. 验收标准

- 新建课包后，`course_packages.id` 符合 `PKG-YYYYMMDD-####`。
- 新建拼团后，`package_groups.id` 符合 `PG-YYYYMMDD-#####`。
- 新建订单后，`orders.order_no` 符合 `LDPKG-YYYYMMDD-######`。
- console 页面展示和搜索均支持新编号。
- 课包下架、拼团失败、订单退款、支付记录回写均正常。
- 后端单测通过。
- console 回归测试通过。

2. 完成编号生成器与仓库层改造。
3. 改课包创建与拼团创建。
4. 改订单号生成。
5. 更新 console 展示与搜索。
6. 更新测试与种子数据。
7. 执行全量回归验证。
